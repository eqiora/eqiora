stable baseline or a general ranking of the tools. It uses an optimized
**development build** of Eqiora whose distribution version is `0.1.5`;
the published `0.1.5` release does not contain this workflow.

## What was compared

Both tools solve the same dimensionless potential on a square of side
$L=1\,\mathrm{m}$. With physical coordinates $x,y$, let $X=x/L$ and $Y=y/L$:

$$
-\Delta u=\frac{2\pi^2}{L^2}\sin(\pi X)\sin(\pi Y),\qquad
u=0\text{ on the boundary},\qquad
u_{\mathrm{exact}}=\sin(\pi X)\sin(\pi Y).
$$

The sine arguments are dimensionless and the forcing has units
$\mathrm{m}^{-2}$. The shipped model declares wave number in $\mathrm{m}^{-1}$
and source scale in $\mathrm{m}^{-2}$; the driver binds them to
$\pi/L$ and $2\pi^2/L^2$.

Both use uniform quadrilateral Q1 elements, real binary64 arithmetic and the
same two-point tensor Gauss stiffness/load rule. The driver checks the actual
FEniCSx quadrature points and weights. Eqiora uses its installed ordinary
Python compile, mesh, resolve and run APIs with `Eqiora.Scalar`; FEniCSx uses
its ordinary Python and PETSc interfaces.

The solver is BiCGStab, with no preconditioner, zero initial guess, relative
residual tolerance `1e-12`, absolute tolerance `1e-14`, and a limit of 10,000
iterations. **Every solve took one iteration.** The sine load is a single
discrete eigenmode, so this does not measure general Krylov convergence.
Each tool passed an independently recomputed true-residual check.

Eqiora eliminates prescribed boundary coefficients; FEniCSx retains identity
boundary rows. At the finest level, both have 1,089 total and 961 free
coefficients, but their stored systems have 961 and 1,089 rows respectively.
The zero data and initial guess give the same effective free problem.

scope includes GeometryGraph construction and mesh resolution/generation,
including its geometry checks. FEniCSx creates a unit-square mesh. Eqiora's

boundary data and forms, including compilation in a fresh JIT cache for each

**Asm** is assembly. Every Eqiora Asm entry is the inclusive total of **two**
scalar-region finalization calls; the values are not divided by the call count.
Eqiora's exclusive solve self time, outside assembly and linear-solve children,
was **4.086 ms at N=4**, **5.169 ms at N=8**, **11.92 ms at N=16**, **39.52 ms at N=32**.
These profile values do not partition the ordinary execution medians or the
separately measured setup stages.

- **Eqiora assembly:** two scalar-region finalization calls, including numeric
  preparation, representability checks and canonical system construction.
- **Eqiora solve self:** exclusive time outside its assembly and linear-solve
  child spans.
- **Eqiora linear:** one reference-provider call.
- **FEniCSx assembly:** matrix/vector allocation and assembly, lifting, ghost
  accumulation and boundary application.
- **FEniCSx linear:** KSP allocation/configuration, zero guess, solve,
  true-residual acceptance and effective-policy/summary queries.

The original measured Eqiora revision finalized the system for the solve and again while
accepting the Result. That revision shared its live acceptance check with the reacceptance helper
and explains the two assembly calls; Result acceptance remains inside the
ordinary execution timing. It does not explain the remaining exclusive solve
time or the whole runtime gap.

Eqiora's assembly span excludes some earlier mapping work. The substantial
exclusive solve time identifies time outside the recorded child spans; this
campaign does not identify its root cause. It would be misleading to attribute
the runtime gap solely to the linear solver or invent an unmeasured cause.

## Environment and reproduction

The campaign ran on `corgi`, an AMD EPYC 7443P with one socket, 24 physical cores
and 48 logical CPUs. Both tools were pinned to CPU 23 with one worker and one
MPI rank; sibling CPU 47 was monitored. OpenMP, BLAS, MKL, BLIS and Rayon thread
settings were one; no GPU was used. The CPU governors remained `ondemand` and
boost remained enabled. The environment and fresh per-child JIT caches were on
home-backed NFS. Start/finish load and CPU monitoring were retained. This quiet
observational window does not establish a controlled, stable reference machine.

Eqiora used its reference host-serial provider and an authenticated wheel built
from the profiling candidate with Rust 1.89 release settings, fat LTO,
stripping and the existing per-package size optimizations. FEniCSx used
DOLFINx, Basix and FFCx 0.11.0, UFL 2026.1.0 and PETSc 3.25.6 from an isolated
locked conda-forge environment. Both Python interpreters were 3.13.18 and NumPy
was 2.5.4. The receipt records the exact source revision, wheel digest, solved
package/build lock and thread settings; the harness revision is separate from
the wheel's producer revision.

Read the

To collect timings rather than the README's correctness-only example, use

affinity and thread settings. Record the actual environment and build; do not
assume another machine reproduces these timings. No benchmark was rerun to
write this page.

This comparison covers only 2D uniform quadrilateral Q1 Poisson at 4–32 cells
per axis. Three-dimensional Poisson, elasticity, cylinder flow, MPI and GPU
comparisons remain unmeasured here. It establishes neither general PDE speed,
general Krylov iteration complexity nor a release-wide performance guarantee.
