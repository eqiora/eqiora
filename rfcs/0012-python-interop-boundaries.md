# RFC 0012: Python interop boundaries

- Status: Bounded Python control, native-modeling, NumPy/DLPack Result producer, and typed scalar-elliptic Realization slices implemented and verified
- Authors: Eqiora contributors
- Created: 2026-07-17

## Summary

Eqiora exposes a small, typed Python SDK over the public Rust facade. Python
controls immutable model revisions and runs; Rust remains the only
implementation of model meaning. Versioned transaction and artifact payloads
form the control plane, while explicitly owned NumPy and later DLPack buffers
form a separate data plane.

## Motivation

Python is essential for scientific workflows, but a binding generated by
exporting every Rust enum would make the crate layout part of the Python API.
Implementing a second model object graph in Python would be worse: source,
Studio, Rust, and Python could then disagree about the meaning or validation
of the same edit.

The boundary also carries two very different kinds of data:

- small, durable edits, diagnostics, identities, and provenance; and
- large numerical arrays with device, ownership, mutability, and lifetime.

Treating both as JSON copies is slow. Treating both as borrowed pointers is
unsafe and not durable. The design therefore separates the control and data
planes before adding bindings.

## Proposed design

### Layering

```text
public Python package: eqiora
    Model / Revision / Run / Result / Series
                    |
                    v
private native module: eqiora._eqiora
                    |  PyO3
                    v
public Rust facade: eqiora
                    |
      Semantic Model / Realization / Artifact
```

`eqiora._eqiora` is a binding adapter, not a semantics crate. It depends only
on the public `eqiora` facade. Python packages never import internal Rust crate
names and do not recreate relation, clock, graph-commit, or solver rules.

The first supported interpreter range is CPython 3.11 through 3.14 with the
ordinary GIL build. Free-threaded CPython is a separate tested capability; the
module does not claim it merely because PyO3 can compile for it. Because the
first vertical slice uses the NumPy C API, it does not claim stable `abi3`
wheels. Wheel tags describe the ABI actually built and tested.

### Control plane

The control plane contains:

```text
ModelTransactionEnvelopeV1   ordered semantic-model edits
ModelEnvelopeV1              immutable validated model snapshot
RunManifestV1/V2             reproducible run inputs, provenance, and outputs
DiagnosticV1                 structured failure information
```

`ModelTransactionEnvelopeV1` is deliberately narrower than the in-memory
Graph Federation `Transaction`. It admits the Semantic Kernel operations,
`ModelView` definition/removal, and commit preconditions needed by the source
compiler, Python, and Studio. It rejects infrastructure nodes and unknown
ontology schemas. Calling that payload a federation-wide transaction would be
false until a versioned ontology-schema registry can reconstruct third-party
views through their own validators.

Operation order is part of transaction intent and is preserved. Preconditions
are evaluated atomically with the operations. The envelope uses explicit wire
DTOs, a schema identifier, bounded decoding, canonical compact JSON, and a
domain-separated content digest. Decoding reconstructs typed kernel
definitions and a typed `ModelView`; it never derives serialization on the
public in-memory types or bypasses constructors.

The immutable `ModelEnvelopeV1` remains the portable execution input. A
transaction is an edit request, not a replacement for a validated model
snapshot. Python `Model.to_bytes()` therefore emits the model envelope, while
transaction serialization is exposed only on editing/commit objects once the
ergonomic editor is implemented.

### Python object surface

The initial public surface is intentionally small:

```python
model = eqiora.compile(source=source, filename="model.eqi")
field = model.field(model.field_ids[0])
plan = eqiora.resolve(
    model,
    temporal=eqiora.time.Tsitouras45(
        initial_step_s=0.01,
        relative_tolerance=1e-6,
        absolute_tolerances={(field, 0): 1e-9},
    ),
)
result = eqiora.run(
    plan,
    state=eqiora.State.initial(plan),
    until_s=1.0,
)

temperature = result.series(field)
t = temperature.time.numpy(copy=False)
y = temperature.values.numpy(copy=False)
```

`Model`, `Run`, `Result`, and `Series` are opaque handles with documented,
stable operations. Rust enum variants and crate modules are not mirrored into
Python. A source containing zero or multiple models is rejected by the
singular `compile` function; a later `compile_all` API can make plurality
explicit.

`Model` owns one immutable `ModelDocument`. It neither borrows a compiler nor
keeps a draft or source buffer alive. `Model.revision` returns an immutable
`Revision` whose equality and hash cover exact codec, typed Model identity,
semantic revision number, and domain-separated content digest. `Model`
equality and hashing use that exact revision. Consequently, exact replay of
the same artifact preserves object identity semantics, while independently
compiled declarations are not required to have equal digests: allocation of
fresh canonical IDs is observable model identity rather than an incidental
serialization detail.

The bounded editing surface is optimistic and artifact based:

```python
edit = model.preview_value_edit("rate", 2.0)
child = model.commit(edit)
```

`preview_value_edit` resolves only a Field/Parameter alias or exact canonical
ID and returns an immutable `ValueEdit` containing an exact-base value-edit
plan. Preview has no model side effect. `commit` checks the base digest and
graph revision atomically, returns a new immutable child `Model`, and leaves
the base intact. A stale or foreign plan fails without partial mutation. The
child preserves the base document's exact transaction and Model codec;
editing is never an implicit artifact migration. `ValueEdit` equality and
hashing use an exact-plan key containing both the base artifact digest and the
content-addressed ordered transaction digest. Two divergent bases therefore
cannot produce the same edit identity merely because their graph-local
preconditions and operation happen to match.

Opaque handles own or share immutable Rust values, so dropping one Python
handle cannot invalidate another. Supported ordinary-GIL CPython serializes
Python object access in the usual way; longer Rust work detaches only after it
owns or clones every input and does not call Python while detached.
Free-threaded CPython remains unclaimed until separately verified.

### Native model construction

Python-native construction is an ergonomic input to the same compiler, not a
second model semantics:

```text
Eqiora source -> parsed ModelDecl ----+
                                      +-> one typed lowerer -> selected versioned transaction
Python objects -> immutable ModelDraft+
```

The draft is a client-neutral Rust value. `Field`, `Parameter`, `Expression`,
`Relation`, spatial `Domain`, continuum `Representation`, `PhysicalDomain`,
`ConservingPort`, and `Connection` are frozen Python handles over that value.
Final graph IDs do not exist while expressions are assembled.
`Model.define(...)` validates the closed declaration set,
lowers it, crosses the selected versioned Model transaction, commits
atomically, and reconstructs the matching canonical Model artifact exactly as
source compilation does. It never generates source text, calls `eval`, or
mutates a partially accepted `Model`.

The registered native 0.1 slice deliberately admits scalar Fields, scalar
Parameters, continuous single- or multi-residual implicit Relations, SI
base-dimension exponents, arithmetic, and time derivatives:

```python
x = eqiora.Field("x", initial=1.0)
rate = eqiora.Parameter(
    "rate",
    value_type=eqiora.ValueType.real(eqiora.Dimension(time=-1)),
    value=1.0,
)
flow = eqiora.Relation(
    "flow",
    residual=eqiora.derivative(x) + rate * x,
)
model = eqiora.Model.define("decay", x, rate, flow)
```

`Relation` receives an explicit zero-valued residual. Symbolic `==` is not
overloaded, and asking for the truth value of a symbolic value raises
`TypeError`; Python control flow cannot silently become model meaning. An
expression retains declaration-local identity, so a same-named Field from a
different draft is still foreign. Names and finite numeric values are checked
at draft closure. Compiler failures replace synthetic internal ranges with a
declaration `graph_path` and never report a fictional source span.

The same slice admits nominal scalar physical Domains, scalar conserving
Ports, `across`/`through` accessors, and anonymous N-ary conserving
Connections. Domain membership is nominal: equal names and dimensions do not
make two independently declared Domains interchangeable. A Connection whose
Port or owning Domain is absent from the closed draft fails before a Model is
returned.

The bounded spatial extension admits runtime-dimensional Cartesian
box/boundary Domains, `Representation.continuum(...)`, supported scalar Fields
and continuous Relations, and closed `grad`, `div`, and `trace` forms. Draft
closure checks exact handle membership only. The shared compiler and
identity-parametric Semantic Kernel typing remain authoritative for dimension,
shape, frame, support, operator, and residual validity. Independently authored
source/Python one-dimensional constant-source Poisson Models therefore share
the central structural fingerprint while retaining distinct exact artifact
identity, and the Python-authored Model can enter the existing Rust scalar FEM
application path.

Native clocks, events, signal Ports, shaped Fields, coordinates and broader
spatial/tensor operators, components, hierarchy, general Python Realization
graph construction, and user-defined callback operators remain non-claims.
They extend the typed draft vocabulary only when the same lowerer and
transaction boundary can admit them without client-specific meaning.

Each `Series` owns its own time and value axes. Eqiora does not manufacture a
global result time array because event and multirate models need not sample
every field on one grid. Source names are ergonomic aliases held by the
compiled model; stable field IDs remain available and survive artifact
round-trip. Names are not silently added to canonical model meaning.

### Data plane and ownership

The initial data plane is host-local, dense, contiguous, read-only `f64` data.
At run completion, each `Array` retains its owned Rust vector without importing
NumPy. The first NumPy projection transfers that allocation once into an
opaque owner. `numpy(copy=False)` and `numpy(copy=None)` return the same
read-only array object without copying. `numpy(copy=True)` explicitly
allocates an independent writable NumPy copy. The no-copy array does not own
its allocation directly, cannot restore its writable flag, and retains its
owner after the originating Result is dropped.

No public object borrows a Rust slice whose owner can be dropped while Python
still holds a view. Unsafe `borrow_from_array`-style ownership is excluded
from the first implementation. Input arrays added later must state accepted
dtype, contiguity, alignment, mutability, and whether a copy occurred.

DLPack 1.x is admitted only as a CPU Result producer. Its read-only flag is
advisory for consumers, so Eqiora's `Array.__dlpack__` never exports Result
storage by alias: `copy=None` and `copy=True` produce a fresh snapshot and
`copy=False` fails with `BufferError`. Legacy capsules, non-`None` streams,
and non-CPU device requests also fail. NumPy owns the versioned capsule,
copied flag, single-consumption state, and exactly-once deleter; Eqiora does
not add a second unsafe capsule implementation. A caller can deliberately
leave the enforced boundary by re-exporting the NumPy view or using native
pointer access, so this is an API ownership contract rather than a memory
sandbox. Array input, GPU, distributed, and sparse layouts remain separate
contracts.

### Long-running execution

After validating Python arguments and cloning the immutable Rust-owned run
inputs, the native adapter detaches from Python for the entire Rust execution.
No solver iteration calls a Python callback. This permits other Python
threads to run and avoids interpreter deadlocks when a Rust backend uses its
own workers.

The first bounded lifecycle is deliberately reference-specific. `run(...)`
and `submit(...).result()` use the same native worker and immutable Result.
`submit(...)` returns a typed `Run` whose public status follows one of these
finite paths:

```text
Queued -> Running | Cancelling | Failed
Running -> Cancelling | Completed | Failed
Cancelling -> Cancelled | Completed | Failed
```

`Created` and `Validating` precede `Queued` in its immutable observation
history. A terminal state cannot be rewritten. `cancel()` records a
best-effort atomic request; the semantic interpreter observes it only between
fully accepted steps, never inside expression evaluation, Newton iteration,
event localization, or atomic activation commit. Completion or failure may win
after the final observable boundary. Only an actually observed request yields
typed cancellation evidence and `EQ0506`; no partial Result is admitted.

Progress is one coalesced snapshot slot, not an event log. Publication is
throttled to 100 ms except for an accepted cancellation boundary, so memory is
constant and Python is never called by the worker. Terminal status, rather
than progress, is the completion authority. The awaitable is a pure-Python
polling projection of the same state: cancelling an asyncio Task or dropping a
Run handle does not implicitly cancel native execution.

The worker retains no Python objects. Native result buffers are removed from
shared state once and cached in one Python Result without holding the lifecycle
lock during materialization. NumPy ownership is created lazily on first array
projection.
Worker panic or lifecycle-lock poison closes the Run as a typed Internal
terminal failure. Result-materialization failure leaves the already completed
native execution intact, but caches one stable Internal projection failure and
wakes every materialization waiter rather than continuing ambiguous state.

The lifecycle records exact Model and reference-plan identities. It does not
name the reference plan a portable Realization. Graph-shaped Realization,
deployment and persisted Run provenance remain prerequisites for production
backend execution through this Python surface.

### Bounded scalar-elliptic Realization

A separate synchronous surface consumes the existing portable-Realization
application service without reflecting its graph types into Python:

```python
request = eqiora.ScalarElliptic(
    method=eqiora.ScalarEllipticMethod.FiniteElement,
    cells_per_axis=32,
)
realization = eqiora.preview_realization(model, request)
result = eqiora.run(model, realization=realization)
```

`ScalarElliptic` is an unbound request, not canonical identity. Preview checks
the exact Model, typed scalar-elliptic profile, bounded implied counts, and the
host-serial capability environment before mesh, matrix, or solver allocation. It returns an
opaque immutable `Realization` containing the accepted exact Model-bound plan
and its content-addressed `RealizationEnvelopeV1`. Repeating an equal preview
is deterministic; selecting FEM or FVM changes accepted identity. Python does
not expose editable graph nodes, backend configurations, or a dictionary
escape hatch.

Execution accepts only that exact Model/Realization pair, detaches from Python,
and calls the existing host-serial scalar-elliptic service. The result projects
only bounded Field location/count/range, continuous balance, and independently
verified linear-solve summaries. Complete numerical arrays stay outside this
control-plane slice.

Every successful result retains a package-neutral `RunManifestV2` with the
exact Model digest, semantic revision, Realization digest, and actual adapter,
backend, host topology, and reduction provenance. `RunManifest.from_json(...)`
uses the accepted Realization's exact replay profile and rejects foreign or
tampered linkage. The execution receipt's exact accepted-output fingerprint is
not a durable `ArtifactDigest`; the Run manifest therefore has an empty output
set rather than inventing a result Artifact.

This path does not inherit the semantic-reference `Run` lifecycle merely
because both are Python APIs. Async submission, cancellation, progress,
timeout, worker/backend/solver choice, production/Rayon/MPI/CUDA execution,
general graph/PDE construction, complete arrays, and durable output Artifacts
remain explicit non-claims.

### Diagnostics

Python raises one of six stable `EqioraError` families:
`ValidationError`, `CompatibilityError`, `CapabilityError`, `ExecutionError`,
`CancellationError`, or `InternalError`. Every failure raised by Eqiora carries
a non-empty tuple of structured diagnostics and a matching machine-readable
`category`. Directly constructed exception objects retain the documented
attributes but have an empty diagnostic tuple because no Eqiora operation
failed.
Each diagnostic exposes stable source, code, severity, message, optional source
span, graph path, and suggestion. `str(error)` is a human rendering, not the
only machine-readable error channel. Ordinary Python argument type errors
remain `TypeError`; invalid Eqiora source, artifacts, realizations, and runs
remain Eqiora diagnostics.

Rust-backed compile, exact replay, run, and Model construction/artifact
operations enter a guarded adapter boundary. An unwinding Rust panic there
becomes a sanitized `InternalError` with one synthetic internal diagnostic. A
process hook wrapper suppresses payload and Rust-location reporting only on the
currently guarded thread and delegates unrelated panics to the previously
installed hook. Pure declaration operators are outside this bounded
containment claim. This is also not a claim that Python can recover from
process abort, memory exhaustion, another extension replacing the global hook
later, or a native dependency compiled without unwinding.

### Packaging and dependency policy

The package uses a PEP 517/518/621 `pyproject.toml`, maturin, and a mixed
Rust/Python layout. The native module is private. Rust dependencies remain
workspace-pinned; Python build metadata records the supported interpreter and
NumPy ranges. Release CI builds wheels in platform-appropriate manylinux,
macOS, and Windows environments and tests the installed wheels rather than
only importing an in-tree extension.

At the 2026-09-03 packaging refresh, the selected implementation baselines are
PyO3 0.29.0, rust-numpy 0.29.0, maturin 1.15.0, and NumPy 2.1 or later. NumPy 2.1 is
the minimum admitted versioned DLPack negotiation surface. PyO3 and rust-numpy
both declare Rust 1.83, within Eqiora's Rust 1.89 MSRV. Versions are
implementation pins, not permanent wire promises.

## Alternatives considered

### Mirror all public Rust types

This makes Python documentation large, exposes crate refactors as breaking
changes, and encourages users to assemble invalid intermediate state. Rejected.

### Implement Python model semantics

This creates a second validator and makes conformance a synchronization
problem. Rejected; Python sends the same typed transactions and artifacts as
every other client.

### Use JSON for numerical arrays

This loses dtype/device information and necessarily copies large results.
Rejected from the data plane.

### Borrow result slices from Rust owners

This can be made safe with a carefully linked base object, but it adds an
unsafe lifetime boundary without benefit when completed results already own
their buffers. Rejected for the first slice in favor of ownership transfer.

### Claim one global time axis

This fits simple ODE examples but fails for multirate and event-sampled fields.
Rejected; every series carries its actual sampling axis.

### Enable `abi3` immediately

The NumPy C API and free-threaded interpreter support require a wheel matrix
that is narrower than PyO3's theoretical ABI support. Rejected until installed
wheel evidence proves the exact combination.

## Compatibility and migration

Python API, transaction wire, model artifact wire, and native ABI are four
separate compatibility surfaces. A Python minor release may wrap a newer
native implementation without changing wire v1. Unknown wire versions fail
closed. Pre-1.0 Python API changes follow project semver and release notes;
accepted v1 wire bytes are never reinterpreted in place.

## Verification

The first vertical slice must prove one path end to end:

1. compile Eqiora source in Python through the Rust compiler;
2. atomically commit its typed transaction;
3. build and round-trip a canonical `ModelEnvelopeV1`;
4. run the reference interpreter while detached from Python;
5. select a field by source name and stable ID;
6. obtain field-local time/value NumPy arrays without a data copy;
7. retain arrays safely after intermediate Python handles are dropped;
8. receive structured diagnostics for malformed source and invalid settings;
9. define the same decay relation from frozen native declarations, round-trip
   its artifact, and reproduce the source model's reference trajectory without
   claiming equal canonical digests for independently allocated identities;
10. reject foreign same-named declarations, symbolic truth tests, invalid
    dimensions, non-finite values, and invalid native argument types without
    partial model mutation;
11. define and exactly replay one nominal scalar-physical triple with a
    multi-residual Relation and N-ary conserving Connection, while rejecting
    foreign nominal Domains and omitted Connection members without a partial
    Model;
12. expose exact immutable revision identity, prepare one value edit, commit it
    to an exact-codec child, and reject stale or foreign edits without mutation;
13. preserve structured diagnostics through the stable exception families and
    contain an injected Rust panic as a sanitized `InternalError`;
14. compare independently authored source/Python scalar, scalar-physical, and
    bounded spatial Models through the shared structural fingerprint while
    preserving distinct exact artifact identity; and
15. define a one-dimensional Cartesian constant-source Poisson Model from
    frozen native declarations, reject foreign/omitted spatial identities and
    a shared-typing support mismatch, then reaccept the Model through the
    existing Rust scalar FEM application path; and
16. preview one typed scalar-elliptic request into a deterministic exact
    model-bound Realization, execute the accepted FEM and FVM profiles through
    host serial while detached from Python, retain accepted Field/balance/solve
    summaries and Run v2 provenance, replay that manifest through its exact
    Realization profile, and reject foreign/tampered Model or Realization
    linkage before execution; and
17. retain one Result Array without importing NumPy, project an irreversible
    read-only zero-copy ndarray with exact CPU descriptor and owner-drop
    lifetime, produce independent versioned DLPack snapshots, and reject
    legacy, no-copy, stream, and non-CPU requests before capsule publication.

Rust unit tests cover bounded transaction-wire round trips and rejection.
Python tests run against an installed package on every claimed interpreter.
A wheel platform graduates only after its built artifact passes the same
vertical slice. Complete native model vocabulary, shaped values, broad spatial
and hybrid/hierarchical authoring, general graph-shaped Python Realization and
production run lifecycle, portable-Realization arrays, array inputs, zero-copy
DLPack, callbacks, notification streams, JAX/PyTorch, GPU data, and user-defined
Python callback operators are explicit non-claims in this milestone. The
separately registered semantic-reference Run lifecycle is a narrower
capability.

## Security, safety, and governance

Source and JSON are untrusted. Wire decoding is bounded and reconstructs typed
values before commit. Array size arithmetic is checked before allocation.
Python object lifetimes own every exposed buffer. The first slice introduces
no Eqiora-authored unsafe Rust; FFI unsafety remains inside reviewed upstream
PyO3/numpy adapters.

Changes to admitted transaction operations, ownership, mutability, implicit
copy behavior, diagnostic shape, or supported interpreter/ABI matrix require
review because they cross language and compatibility boundaries.

## Unresolved questions

- The schema-registry contract needed for federation-wide transactions and
  third-party ontology views.
- Whether source symbol aliases become a separately versioned debug/symbol
  artifact rather than model meaning.
- General and production Realization/deployment cancellation, progress,
  timeout, array, and durable output contracts.
- Typed array-input ownership and stream synchronization for the first GPU
  result backend.
